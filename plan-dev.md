# Визуальный конструктор Telegram-ботов для Windows

## 1. Назначение продукта

Нативное Windows-приложение предназначено для визуального создания и управления Telegram-ботами без написания кода.

Приложение должно позволять пользователю:

- подключать Telegram-ботов;
- создавать сценарии работы через визуальный конструктор;
- запускать и останавливать ботов;
- автоматически запускать приложение и выбранных ботов вместе с Windows;
- продолжать работу ботов после закрытия основного окна;
- работать с пользователями ботов;
- хранить пользовательские данные;
- использовать переменные, теги и пользовательские поля;
- работать с вложениями;
- создавать рассылки;
- обрабатывать ошибки без отображения технических сообщений обычному пользователю;
- соблюдать ограничения Telegram Bot API;
- проверять сценарии до публикации;
- хранить состояние сценариев между перезапусками приложения;
- вести понятный журнал событий;
- поддерживать расширение возможностей Telegram без изменения существующих пользовательских проектов.

Главный принцип интерфейса: пользователь без технических знаний должен иметь возможность создать и запустить базового бота без знания Telegram Bot API, HTTP, JSON, webhook, callback query и других технических терминов.

## 3. Основная модель сценариев

Сценарии строятся из следующих логических элементов:

1. Событие
2. Условие
3. Действие
4. Ожидание
5. Ветвление
6. Переход
7. Завершение

Базовая модель выполнения:

```text
Событие
  ↓
Условия
  ↓
Действия
  ↓
Ожидание или ветвление
  ↓
Следующий блок или другой сценарий
```

Каждый выполняемый блок должен поддерживать внутренний результат выполнения.

Минимальные типы результата:

- успешно;
- ошибка;
- таймаут;
- альтернативная ветка.

Основной интерфейс конструктора не должен показывать технические ветки обработки ошибок по умолчанию.

```text
Запускать Bot Agent вместе с Windows
```

У каждого бота должен существовать отдельный параметр:

Если пользователь закрывает основное окно, Bot.Agent может продолжать работу.

Первичное действие закрытия должно позволять выбрать:

- продолжить работу в фоне;
- полностью завершить приложение и ботов;
- сохранить выбранное поведение.

### 5.4. Системный трей

Через трей должны быть доступны:

- открытие приложения;
- текущий статус ботов;
- пауза всех ботов;
- выход из приложения.

### 5.5. Состояния бота

Минимальные состояния:

- Запускается
- Работает
- Приостановлен
- Нет подключения
- Требует внимания
- Ошибка авторизации
- Остановлен из-за критической ошибки

## 6. Подключение к Telegram

Серверный runtime пользователя принимает Telegram Update через webhook. Windows-приложение используется как панель настройки и управления.

Основная цепочка:

```text
Telegram
  ↓
HTTPS-домен пользователя
  ↓
Reverse proxy
  ↓
Bot.Agent на сервере пользователя
  ↓
Update Queue
  ↓
Flow Engine
```

Для каждого бота Bot.Agent регистрирует отдельный HTTPS URL через `setWebhook`.

Внутренний endpoint Bot.Agent доступен только на loopback-интерфейсе сервера:

```text
http://127.0.0.1:8443/webhook/{bot_id}
```

Публичный адрес `https://<домен-пользователя>/webhook/{bot_id}` направляется reverse proxy на внутренний endpoint. Пользователь предоставляет собственный сервер и домен. Cloudflare, сторонний туннель и открытие порта на Windows-компьютере не требуются.

HTTPS завершается на reverse proxy с публично доверенным сертификатом. Внутреннее соединение до Bot.Agent остаётся на loopback-интерфейсе сервера. Приложение не должно отключать проверку TLS-сертификатов.

В приложении настраиваются публичный адрес сервера, параметры первоначального подключения по SSH и ключ доступа к API Bot.Agent. SSH применяется для установки и обновления Agent; постоянное управление выполняется через защищённый HTTPS API. Bot token, SSH-ключи и API-ключи хранятся в защищённом хранилище и не записываются в журнал.

При регистрации webhook обязательно задаётся случайный `secret_token`. Каждый входящий запрос проверяется по заголовку:

```text
X-Telegram-Bot-Api-Secret-Token
```

Секрет webhook хранится зашифрованно и не записывается в журнал.

Webhook endpoint должен быстро проверить запрос, сохранить Update в устойчивую очередь и вернуть успешный HTTP-ответ. Выполнение сценария не должно блокировать приём следующих webhook-запросов.

При временной ошибке до надёжного сохранения Update endpoint возвращает неуспешный HTTP-статус, чтобы Telegram мог повторить доставку.

Webhook является единственным механизмом получения Telegram Update.

При запуске бота приложение сверяет текущий webhook через `getWebhookInfo` и обновляет его, если URL или настройки отличаются. При явной остановке бота webhook удаляется без удаления ожидающих Update.

Для каждого Telegram Update необходимо хранить идентификатор update и выполнять дедупликацию.

Telegram не гарантирует бесконечное хранение необработанных обновлений. Обновления Telegram хранятся ограниченное время, поэтому длительный офлайн-режим может приводить к потере событий.

## 7. Главный экран

Главный экран содержит список подключенных ботов.

Для каждого бота отображаются:

- название;
- username;
- состояние;
- количество известных пользователей;
- время последнего события;
- действие открытия.

Основное действие главного экрана:

```text
Добавить бота
```

Внутри бота доступны основные разделы:

- Конструктор
- Пользователи
- Рассылки
- Журнал
- Настройки

---

## 8. Подключение Telegram-бота

Пользователь подключает существующего Telegram-бота через токен BotFather.

После ввода токена приложение выполняет проверку подключения.

После успешной проверки отображаются:

- название бота;
- username;
- статус токена;
- доступная базовая информация о боте.

Полный токен после сохранения не отображается в обычном интерфейсе.

Токены и другие секреты не должны храниться в открытом виде.

Секреты не должны записываться в обычный журнал событий.

Редкие и технические Telegram-параметры скрываются в разделе:

```text
Дополнительно
```

Для блока отправки сообщения основной интерфейс содержит:

- содержимое;
- кнопки;
- вложение.

Расширенные параметры могут содержать:

- отключение уведомления;
- защиту контента;

- message thread;
- link preview;
- message effect;
- Business connection;
- дополнительные Telegram-параметры.

## 11. Версионирование сценариев

Каждый сценарий имеет минимум два состояния:

- Черновик
- Опубликованная версия

Изменение черновика не должно изменять выполняющуюся опубликованную версию.

Публикация выполняется отдельным действием.

Перед публикацией сценарий проходит автоматическую проверку.

---

## 12. Проверка сценария

Валидатор должен обнаруживать как минимум:

- переход на отсутствующий сценарий;
- переход на отсутствующий блок;
- использование неизвестной переменной;
- превышение Telegram-лимитов;
- отсутствие необходимых прав;
- несовместимость действия с типом чата;
- отсутствующее вложение;
- неправильную конфигурацию кнопок;
- неправильный тип переменной;
- потенциально бесконечный цикл;
- недостижимый блок;
- некорректную payment-схему;
- некорректную конфигурацию ожидания.

Ошибки должны быть привязаны к конкретному блоку конструктора.

## 13. Переменные

Система переменных должна поддерживать области видимости.

### 13.1. Системные переменные

Примеры:

```text
system.now
system.date
```

Системные переменные доступны только для чтения.

### 13.2. Переменные события

Примеры:

```text
event.message.text
event.message.id
event.chat.id
```

Существуют в рамках обработки конкретного события.

### 13.3. Переменные запуска сценария

Пример:

```text
flow.order_id
```

Существуют в рамках конкретного запуска сценария.

### 13.4. Переменные пользователя

Примеры:

```text
user.phone
user.city
user.order_number
```

Сохраняются между сессиями.

### 13.5. Переменные чата

Пример:

```text
chat.language
```

Сохраняются для конкретного чата.

### 13.6. Переменные бота

Пример:

```text
bot.support_chat
```

Хранят общие настройки и данные конкретного бота.

### 13.7. Secret-переменные

Используются для:

- API-ключей;
- токенов;
- паролей;
- других секретов.

Secret-переменные хранятся зашифрованно и не выводятся полностью в интерфейсе или логах.

### 13.8. Типы переменных

Минимально поддерживаются:

- Текст
- Число
- Да/Нет
- Дата и время
- Список
- Объект/JSON

## 14. Подстановка переменных

Переменные используются в текстах и параметрах блоков.

Пример:

```text
Здравствуйте, {user.first_name}!
Ваш заказ: {user.order_number}
```

При вводе `{` интерфейс должен отображать доступные переменные.

## 15. Пользователи ботов

Пользователь появляется в локальной базе после взаимодействия, которое Telegram передал боту.

Telegram Bot API не предоставляет боту произвольный глобальный список пользователей Telegram.

Обычный бот не может начать личный разговор с произвольным пользователем, который ранее не начал взаимодействие с ботом допустимым способом.

Карточка пользователя должна содержать:

- Telegram ID;
- username;
- имя;
- фамилию;
- язык;
- дату первого взаимодействия;
- дату последнего взаимодействия;
- статус;
- теги;
- пользовательские поля;
- текущие ожидающие состояния;
- текущий сценарий;
- историю событий.

Telegram ID хранится в 64-битном целочисленном типе.

## 17. Пользовательские поля

Пользовательские поля хранят дополнительные данные пользователя.

- название;

## 18. Сегменты

Сегмент является сохраненным набором условий по пользователям.

Сегмент может учитывать:

- теги;
- поля;
- язык;
- дату первой активности;
- дату последней активности;
- статус;
- значения пользовательских данных.

Сегменты используются для рассылок и фильтрации списка пользователей.

---

## 19. Вложения

Файлы должны храниться в отдельной библиотеке вложений.

Минимальная структура вложения:

```text
Asset
- internal_id
- filename
- mime
- size
- hash
- local_copy
- telegram_file_ids
```

Telegram `file_id` должен храниться отдельно для каждого бота.

Повторная отправка уже загруженного файла должна использовать Telegram `file_id`, когда это возможно.

До запуска сценария приложение должно проверять Telegram-ограничения на размер и тип файла.

---

## 20. Ожидание ответа

Блок ожидания ответа не должен удерживать активный поток выполнения.

Состояние ожидания сохраняется в базе данных.

Минимальные данные ожидания:

```text
user_id
chat_id
thread_id
expected_event
flow_version
resume_node
expires_at
```

После перезапуска приложения или Windows ожидание должно продолжить работу.

---

## 21. Задержки и расписания

Отложенные действия хранятся постоянно.

Задержка не должна реализовываться через длительный `sleep`.

Для каждого отложенного действия сохраняются:

- бот;
- сценарий;
- версия;
- пользователь;
- чат;
- блок продолжения;
- время выполнения;
- состояние.

После перезапуска Bot.Agent просроченные и ближайшие задачи восстанавливаются из хранилища.

---

## 22. Рассылки

Рассылка является отдельной сущностью.

Для рассылки задаются:

- получатели;
- сегмент;
- сообщение;
- вложения;
- кнопки;
- время запуска;
- статус.

Перед массовой отправкой должна существовать тестовая отправка.

Статусы рассылки:

- Черновик
- Запланирована
- Выполняется
- Приостановлена
- Завершена
- Ошибка

Во время выполнения отображаются:

- всего получателей;
- отправлено;
- в очереди;
- ошибки;
- пропущено.

---

## 23. Очередь исходящих сообщений

Сценарии не должны напрямую выполнять Telegram send-методы.

Все отправки проходят через:

```text
Flow Engine
  ↓
Outbox
  ↓
Rate Limiter
  ↓
Telegram Adapter
  ↓
Telegram API
```

Outbox должен обеспечивать:

- очередь;
- порядок отправки;
- повторные попытки;
- планируемое время отправки;
- учет ограничений Telegram;
- остановку и продолжение;
- сохранение между перезапусками.

---

## 24. Ограничения скорости Telegram

Приложение должно учитывать ограничения Telegram и автоматически регулировать скорость отправки.

При получении `429 Too Many Requests` необходимо использовать значение `retry_after`, возвращенное Telegram.

Ограничение скорости не должно отображаться пользователю как техническая ошибка сценария.

---

## 25. Обработка ошибок

Технические ошибки Telegram преобразуются в понятные пользователю сообщения.

Обычный интерфейс не должен показывать:

- HTTP-коды без пояснений;
- raw JSON Telegram;
- stack trace;
- необработанные exception;
- внутренние названия Telegram API методов.

Типы ошибок должны обрабатываться раздельно.

### 25.1. Нет подключения к интернету

Поведение:

- бот остается активным логически;
- отображается статус отсутствия подключения;
- выполняются автоматические повторные подключения.

### 25.2. Telegram timeout или 5xx

Поведение:

- автоматическая повторная попытка;
- увеличивающаяся задержка между попытками.

### 25.3. Telegram 429

Поведение:

- использовать `retry_after`;
- перенести отправку на указанное время.

### 25.4. Неверный или отозванный токен

Поведение:

- остановить конкретного бота;
- остальные боты продолжают работать;
- показать необходимость переподключения.

### 25.5. Недостаточно прав

Поведение:

- не выполнять невозможное действие;
- показать, какое право отсутствует;
- указать конкретный блок сценария.

### 25.6. Некорректный параметр

Поведение:

- не выполнять бесконечные повторные попытки;
- зарегистрировать ошибку блока;
- показать причину в журнале.

### 25.7. Недоступный пользователь или чат

Поведение:

- пропустить конкретного получателя;
- продолжить другие выполнения;
- обновить состояние пользователя при необходимости.

### 25.8. Миграция группы

При наличии Telegram `migrate_to_chat_id` локальный идентификатор чата должен обновляться автоматически.

---

## 26. Изоляция ошибок

Ошибка одного пользователя или одного execution не должна останавливать:

- других пользователей;
- другие сценарии;
- другие рассылки;
- весь бот;
- другие боты.

Каждый Telegram Update выполняется в отдельном execution context.

---

## 27. Dead Letter

События и действия, которые не удалось корректно выполнить после допустимых попыток, сохраняются отдельно.

Для записи Dead Letter сохраняются:

- время;
- бот;
- пользователь;
- чат;
- сценарий;
- версия сценария;
- блок;
- событие;
- причина;
- число попыток;
- технические данные.

Пользователь может:

- открыть проблемный сценарий;
- повторить действие;
- пропустить событие.

Rich Messages должны поддерживаться отдельным типом сообщения.

Поддерживаемые элементы определяются текущими возможностями Telegram Bot API.

Для Telegram streaming-ответов система должна хранить состояние активной генерации и корректно завершать или отменять ее согласно доступным методам Bot API.

Ephemeral-функции Telegram должны быть представлены отдельными возможностями Telegram Adapter.

Guest Mode обрабатывается как отдельный Telegram-контекст.

## 46. Communities

Telegram Community events должны преобразовываться в отдельные события конструктора на основании актуального Bot API.

## 47. Managed Bots

Managed Bots должны быть представлены отдельным набором Telegram-действий и событий.

Токены управляемых ботов относятся к секретам и подчиняются тем же правилам безопасного хранения.

## 48. Bot-to-Bot

Для bot-to-bot взаимодействий обязательно используются:

```text
execution_id
origin_bot_id
depth
deduplication_key
timeout
```

В движке должно существовать ограничение максимальной глубины цепочки.

Повторяющиеся события должны дедуплицироваться.

Это предотвращает бесконечные циклы между ботами.

---

## 49. Payments

Telegram Payments должны быть реализованы отдельным набором сценарных блоков.

Платежный процесс должен различать:

- создание счета;
- pre-checkout;
- подтвержденную успешную оплату;
- неуспешную оплату;
- возврат при поддержке соответствующего платежного режима.

`pre_checkout_query` не считается подтверждением получения оплаты.

Фактом успешной оплаты является соответствующее Telegram событие успешного платежа.

---

## 50. Telegram Stars

Для цифровых товаров и услуг внутри Telegram используются Telegram Stars в соответствии с текущими требованиями Telegram.

Stars-функции должны быть отделены от обычных платежей за физические товары и услуги.

Поддерживаемые операции определяются актуальным Bot API.

### Статус реализации пунктов 30–50

Реализовано на базе Telegram Bot API 10.3:

- единый каталог событий, типов сообщений, действий, прав и допустимых чатов;
- автоматический расчёт `allowed_updates` по опубликованным сценариям;
- преобразование Update в событие конструктора и переменные deep link, Business, Guest, Mini App, Community и платежей;
- структурированные Rich Messages, streaming, ephemeral, Managed Bots, Payments и Stars как отдельные возможности адаптера;
- проверка Privacy Mode, совместимости чата, прав, Rich Message, ephemeral, Stars и обязательного bot-to-bot контекста;
- ограничение глубины bot-to-bot цепочки и обязательный ключ дедупликации.

## 63. Непрерывность работы

Ошибка отдельного блока не должна автоматически завершать Bot.Agent.

Ошибка отдельной рассылки не должна останавливать обычные сценарии.

Ошибка интерфейса не должна приводить к остановке Bot.Agent.

---

## 64. Работа компьютера и фон

Локальный бот работает только когда:

- Windows-компьютер включен;
- пользовательская среда позволяет работу приложения;
- Bot.Agent запущен;
- имеется доступ к Telegram.

Сон, выключение компьютера или системная приостановка могут временно остановить локальный runtime.

После возобновления работы Bot.Agent должен автоматически восстановить соединение и продолжить допустимые ожидающие задачи.

- callback;
- payment events;
- bot-to-bot events;
- восстановленных scheduled actions.

Повторное получение одного и того же Telegram Update не должно повторно выполнять необратимые действия, если оно уже было успешно обработано.

---

## 68. Транзакционность

Изменение критического состояния должно выполняться согласованно.

Перед подтверждением успешной обработки события необходимо сохранить:

- изменение пользовательских данных;
- новое состояние сценария;
- WaitingState;
- Scheduled Action;
- Outbox action;
- статус Execution.

При аварийном завершении приложение должно иметь возможность определить завершенные и незавершенные операции.

Минимальные статусы:

## 72. Статусы пользователя

Минимально система должна отличать:

- пользователя, заблокировавшего бота, если это определено по Telegram-ошибке;

- фильтр по языку;

---

## 77. Требование к развитию

Новые Telegram Bot API версии должны добавляться через обновление Telegram.Adapter, деклараций действий, событий, ограничений и валидаторов.

Существующие опубликованные сценарии должны сохранять работоспособность после обновления приложения, если Telegram не удалил используемую возможность на стороне платформы.

### Статус реализации пунктов 50–77

Реализованы каталог Telegram Bot API 10.3 и валидаторы Stars/paid media, централизованные лимиты, SQLite-сущности и версии сценариев, устойчивые очереди и восстановление, Execution/ExecutionEvents, шифрование секретов, дедупликация, статусы выполнения, расширенная фильтрация и история пользователей, системный журнал, безопасный импорт/экспорт `.nativebot`, а также отдельный для каждого бота выбор webhook или long polling.
